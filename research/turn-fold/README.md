# 整轮过程折叠实验

本实验验证了用户提出的中间路线：**在官方前端生成虚拟列表之前，先把已完成的过程换成一个固定高度的摘要行，再让官方列表显示它。** 不需要修改后端，也不需要重新实现整套聊天界面。摘要可以展开和收起，最终回答继续显示。

目前能实现这种折叠，但还不能保证长会话滚动没有抖动。摘要的高度可以准确预知，旁边的普通正文、工具和特殊通知仍依赖官方的动态测量与滚动补偿。

实验日期：2026-10-18。本目录没有接入正式入口；`src/`、`webui/`、托盘和上游源码未修改。实验没有启动或重启正式后台，没有调用模型，没有写入真实会话。

## 数据与对照方式

真实数据来自 `E:\Desktop\mytests\modeltest` 的“HY3模型评测打分”，在 2026-10-17 20:07:44 香港时间取得只读快照：

- 1393 条消息：242 条用户消息、1142 条助手消息，以及 9 条其他记录。
- 561 个 reasoning、1059 个 tool、538 个 text 内容块。
- 助手文本/推理共 430753 字符，不含用户的 `text` 字段；工具输出文本共 1773775 字符。
- 快照 JSON 为 6915065 字节，约 6.60 MiB；SHA-256 为 `d1dd744769366f0fd5a5b32f665c093f191b54aac05f3ab80a613a078652d6d5`。
- 216 轮符合本实验的折叠条件。记录中没有 `idle` 消息，判定使用已有的消息完成时间、错误/工具状态和当前会话状态。

另有一个合成会话：100 轮、200 条消息、1000 次读取工具调用。每轮交替包含 10 段中途说明与工具，最后附最终回答。它用来验证大量过程内容的折叠和展开，不代替真实长会话的负载测量。

对照组和实验组使用同一份官方发布资源、同一份会话快照、同样的 Playwright 夹具、1280×760 视口和隔离 Chromium。每次运行只有一个 worker，各组串行执行。对照组只加入计时观测，保留官方行投影和布局；实验组加入过程折叠补丁。没有叠加项目的 Codex 外壳样式。

三个性能场景：

1. `hy3-full`：一次提供全部 1393 条消息的压力实验，不代表正常打开会话的加载方式。
2. `process-full`：一次提供合成会话，做 18 次上滚；实验组额外连续展开/收起同一摘要 8 次。
3. `hy3-paged`：使用官方的分页行为，首批 40 条、之后每批 20 条，通过真实滚轮输入一直加载至最早消息，共 69 页。分页接口由本地夹具回放。

## 实测结果

最终数据来自 `verified-baseline-01`、`verified-grouped-01`、`verified-baseline-02`、`verified-grouped-02`。每次 5 项浏览器检查全部通过，共 20 次测试执行；折叠专用断言只在实验组运行。另有 4 项单元检查、18 个断言通过。各次结果保存在 [evidence.json](./evidence.json)，以下范围表示两次重复的最小值至最大值，不是置信区间。

| 场景 | 模式 | 就绪 / 秒 | 继续分页至全部 / 秒 | 全部虚拟行数 | 最终 JS 堆 / MiB | 渲染进程 Private / MiB |
|---|---|---:|---:|---:|---:|---:|
| HY3 一次全量 | 官方 | 1.46–1.55 | — | 1556 | 35.22–35.24 | 134.89–135.20 |
| HY3 一次全量 | 整轮折叠 | 1.60–1.61 | — | 1061 | 35.14 | 141.64–142.82 |
| 过程密集合成 | 官方 | 1.14–1.21 | — | 2299 | 25.99–26.06 | 100.26–101.75 |
| 过程密集合成 | 整轮折叠 | 1.17–1.18 | — | 399 | 25.19–25.22 | 101.01–101.48 |
| HY3 官方分页 | 官方 | 0.85–0.97 | 21.56–25.90 | 1556 | 38.81–39.08 | 189.37–202.31 |
| HY3 官方分页 | 整轮折叠 | 1.01–1.04 | 22.63–22.88 | 1061 | 38.00–38.41 | 201.49–202.14 |

真实会话虚拟行数减少约 **32%**，过程密集合成会话减少约 **83%**。但官方本来就只挂载屏幕附近的少量行，且原始消息仍保留在客户端，所以内存没有同比下降。全量压力场景的就绪略慢；分页总耗时落在对照组两次波动范围内，没有得到普遍加速的证据。

分页全载后的专用浏览器进程合计 Private：官方 **271.74–284.97 MiB**，折叠 **283.63–284.48 MiB**；Working Set 分别为 **446.06–459.83 MiB**、**459.70–461.93 MiB**。这里的整个浏览器内存明显高于 JS 堆数字，不能把约 38 MiB 当作页面的全部内存。

额外分组成本：

| 场景 | 调用数 | 额外分组累计 / ms | 单次最大 / ms |
|---|---:|---:|---:|
| HY3 一次全量、首次就绪 | 2 | 45.0–46.6 | 26.5–27.8 |
| HY3 全部分页过程 | 70 | 559.3–604.3 | 19.3–22.1 |
| 合成会话，含 8 次展开/收起 | 18 | 154.3–215.3 | 13.1–16.7 |

分页首批仅 40 条，额外分组累计为 **1.3–2.1ms**。后续数据变多时成本也增加。这个规模上计算压力可控，但单次约 20–28ms 已经可能跨过一帧，仍有增量处理的优化价值；没有依据把它说成免费或常数时间。

两次各 8 个展开/收起循环，共 16 个循环，摘要条操作前后的最大位置偏移均为 **0px**。点击至断言完成约 **84–186ms**，含自动化等待开销。两轮循环前后强制 GC 的 JS 堆分别增加 **0.54 / 0.47 MiB**，没有观察到每次重建全部工具正文造成的大幅累积；这种有限次数检查不能证明长期无泄漏。

普通历史滚动没有解决：

| 场景 | 官方每轮最大额外位移 | 折叠每轮最大额外位移 |
|---|---:|---:|
| HY3 一次全量 | 204 / 36px | 179 / 179px |
| 过程密集合成 | 46 / 46px | 135 / 135px |

尤其在本次过程密集场景，折叠后的单次最大位移更大。因此不能将“摘要本身的高度准确”和“整条时间线滚动平滑”视为同一件事。后续若继续做稳定性修复，应针对普通行的测量缓存和滚动锚定；仅增加后端分组标记不足以解决这些几何变化。

计时与内存的含义：

- “就绪”包含夹具准备、页面导航、字体和已挂载行高度检查，不是产品的严格首屏指标。“载入全部历史”从首批就绪后开始，包含自动滚动、分页和状态等待；不代表后端传输 6.60 MiB 要用这么久。
- JS 堆的最终值在强制 GC 后采样；初始值没有强制 GC，不能直接以差值判断泄漏。进程 Private/Working Set 是 CDP 列出的专用测试 Chromium 进程的 Windows 快照，不是峰值。两类内存不可混为同一个数字。
- 分组耗时用 `performance.now()` 包围前端函数调用，单独列出官方投影与额外分组成本。它是这一阶段的执行耗时，不是整台机器的 CPU 使用率。
- `process-full` 实验组比对照组多执行了 8 次展开/收起，因此该场景的累计 script/task 时间不能直接用于组间性能排名。

滚动测量先上滚 1800px，再做 18 次 240px 上滚，比较前后都可见的同一行相对屏幕的移动量与输入量的差。每次采样必须依次收到本次 `wheel`、`scroll`、`scrollend`。先前只等待 `scrollend` 的版本可能提前收到上一轮的结束事件，旧结果保留作诊断，不作为最终滚动结论。

这个指标是操作前后的额外位移，不是逐帧最大闪动，也不是 CLS。相同滚动距离在折叠前后对应不同内容；两次重复也不足以推断普遍排名。能确认的是有非零位移，不能宣称整页已经无抖动。

## 前端实际做了什么

`groups.mjs` 先接收官方 `constructSessionMessageRows` 的结果，按用户轮次整理助手内容。仅当该轮已完成、无助手错误/重试、工具全部完成，且不是当前正在运行的轮次时，才折叠最后正文之前的普通助手行。最终回答的连续尾部文本块全部保留，不只留下最后一段。错误轮次、未完成轮次保持原样；压缩通知、独立 Shell 等特殊行不被替换。

折叠时，原过程行从虚拟列表的输入中移除，换成一个真正的官方行类实例。摘要独立占 **40px**，里面显示“用时 … · … 次工具调用 · 展开过程”。展开后摘要保留，原过程行以原对象恢复到列表中，继续采用官方虚拟化和原生工具折叠。不是在 DOM 已经渲染后把内容压成零高。

这里的“用时”是用户消息创建至该轮最后助手完成的时间差，不是模型纯推理用时；工具数来自已有工具内容块。后端不需要为这两个数字新增字段。

当前缓存只复用已分析消息的元数据和摘要行，不复制大型工具正文。**结构更新和切换仍会调用官方投影，并遍历已加载消息的结构字段。** 这还不是完整的增量索引；折叠也没有把原始消息从客户端状态中卸载。不能将它解释为“所有数据只处理一次”或者“内存按折叠行数等比例下降”。

## 这次定位并修正的两个问题

**固定高度必须在整条测量链路中一致。** 官方列表默认把未知行估为 60px。只把摘要的 `estimateSize` 改成 40px 会让这个版本进入启动测量循环：核心认为实测值等于估值，不写入高度缓存；外层去重仍把缓存缺失当 60px，于是不停重新提交 40px。补丁同时修改了摘要估值与测量去重的默认值，并避免高度估计订阅响应式依赖。

**展开时要处理底部跟随和锚点。** 官方在内容不足一屏时，取消底部跟随的操作直接返回。若在展开前调用它，展开后的内容仍会被拉向底部。实验先应用展开并更新总高度，再取消跟随，最后使用官方锚点保持摘要条相对视口的位置。短会话与长会话都单独检查了这种行为。

因此，“运行时动态修改一部分代码”确实可行；但需要接入列表内部的行生成、测量和锚定，不能只改网页表面样式。后端的完成标记可以帮助判断边界，却无法自动解决浏览器布局的高度变化。

## 验证范围和限制

- 浏览器功能检查覆盖：摘要出现、过程从 DOM 中移除、展开恢复、再次收起、最终回答保留、短会话展开时摘要位置误差不超过 1px，以及完成事件后自动折叠。
- 运行中检查发送官方夹具构造的 `session.step.ended` 和 `session.execution.succeeded` 事件；验证的是 UI 状态变化，没有发起模型请求。尚未做这次自动折叠过渡的逐帧视觉保证。
- 单元检查覆盖最终多段文字保留、原消息不变、原行对象恢复、运行/失败工具不折叠、缓存状态失效，以及发布脚本的语法和未知指纹处理。
- 保守判定依赖数据中可观察的状态。无法从任意文本语义推断“这是最终回答”；如果某种中断没有留下可区分的状态，本实验不保证能正确辨认。多窗口、切换会话后的缓存回收、深链接定位隐藏工具、移动端、巨大 diff/图片和窗口宽度变化尚未系统验证。
- 继续使用官方虚拟化，没有使用上一份 `runtime-fold` 实验的“少量行全部提前挂载”策略。那次有限样本的 0px 结果不能套用到这里。

## 本机复现

需要 Bun、参考源码目录已有的 Playwright 依赖和测试浏览器，以及已保留的 `.cache` 快照。测试默认完全离线，正式后台可以关闭。`OPENCODE_SOURCE` 可覆盖参考源码路径。

```powershell
Set-Location 'E:\Desktop\mytests\opencode-web\research\turn-fold'
bun test ./groups.test.mjs

$env:OCW_GROUP_MODE = 'baseline'
$env:OCW_GROUP_RUN = 'baseline-new-run'
bun run run.mjs --max-failures=1

$env:OCW_GROUP_MODE = 'grouped'
$env:OCW_GROUP_RUN = 'grouped-new-run'
bun run run.mjs --max-failures=1

bun summarize.mjs baseline-new-run grouped-new-run
```

每次使用新运行名，以保留旧记录。Playwright 管理独立的 `127.0.0.1:53127` 实验代理并在结束后关闭；代理拒绝真实 API、鉴权及非 GET/HEAD 请求，不能作为普通聊天客户端使用。所有外网请求由性能测试阻断。

`capture.mjs` 用于重新只读捕获指定会话，需要已有后台运行，会替换本地快照；复现当前数据不需要执行它。默认不获取缺失的官方资源；只有显式设置 `OCW_FETCH_MISSING=1` 才会读取已有后台的静态资源。

`.cache/` 含真实会话内容和静态资源，已忽略；`test-results/` 保存本地原始结果与失败诊断，也已忽略。报告和汇总只保存统计数字；示意截图使用合成会话。
